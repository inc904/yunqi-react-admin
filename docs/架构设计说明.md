# 前端架构设计说明

## 结论先行

本项目采用**轻量级的 Feature-based（按业务功能组织）架构**，借鉴 Feature-Sliced Design（FSD）的“层、业务切片、技术分段”思想；它不是完整照搬 FSD，也不是为了形式而拆文件。

运营后台的商品、订单、会员、营销、权限等领域相对独立，却都会共享登录态、请求能力、分页、抽屉和展示格式化。若只按文件类型放置（把所有页面放进 `pages/`、所有组件放进 `components/`），一个领域变更往往要跨多个大目录寻找文件；若每页自带一套请求和 UI，又会造成复制粘贴。当前结构在两者之间取平衡。

## 参考依据

1. [Redux 官方风格指南：按 Feature Folder 组织](https://redux.js.org/style-guide/#structure-files-as-feature-folders-with-single-file-logic) 建议把同一功能的逻辑集中在同一个功能目录，而非按技术类型分散；虽然本项目未使用 Redux，这一高内聚原则仍然适用。
2. [Feature-Sliced Design 概览](https://feature-sliced.design/docs/get-started/overview) 将前端代码分为应用层、业务切片和共享层；切片按业务域命名，切片内部可再按 UI、API、模型、工具等目的组织，目标是让项目面对变化仍保持可理解、可演进。
3. [React 官方：共享状态](https://react.dev/learn/sharing-state-between-components) 建议把需要协调的状态放到最近公共父级，作为单一事实来源。项目中 `App` 管理登录态，`ConsoleLayout` 通过 props 读取身份与退出回调，即为此原则的应用。

## 当前目录与职责

```text
src/
├─ App.tsx                  # 应用入口：登录态恢复、路由组合
├─ api.ts                   # HTTP 边界：Axios、JWT、错误转换、响应信封
├─ types.ts                 # 跨领域的数据契约，例如 Product、Order、Auth
├─ constants/               # 声明性配置，例如菜单—路由—权限映射
├─ hooks/                   # 可复用的数据生命周期，例如 useRequest/usePage
├─ lib/                     # 无副作用的展示转换，例如金额、时间、状态文案
├─ components/
│  ├─ layout/               # 仅负责应用壳：侧栏、顶栏、内容区
│  └─ ui/                   # 无业务知识的 UI：分页、抽屉、Loading、Toast
└─ features/
   ├─ auth/                 # 登录
   ├─ dashboard/            # 经营指标与趋势
   ├─ products/             # 商品筛选、编辑、上下架
   ├─ orders/               # 订单筛选、详情、发货
   ├─ catalog/ customers/   # 分类、会员
   ├─ marketing/            # 优惠券、Banner
   └─ system/               # 管理员、角色、日志
```

## 设计原则与本项目的落点

| 原则         | 在项目中的实现                                                              | 获得的效果                            |
| ------------ | --------------------------------------------------------------------------- | ------------------------------------- |
| 高内聚       | `features/products` 内放商品列表、商品抽屉、上/下架                         | 新增 SKU 或商品审核时优先只改一个目录 |
| 低耦合       | `components/ui` 不导入 `Product`、`Order` 等业务类型                        | 分页、抽屉、提示可以被所有领域复用    |
| 明确依赖方向 | `App → features/components → hooks/lib/api/types`；共享层不反向导入业务功能 | 避免循环依赖；布局不依赖登录页面实现  |
| 单一事实来源 | 登录态只由 `App` 保存；页面局部筛选只留在对应功能页                         | 避免多份 token、页码或筛选条件不同步  |
| 边界适配     | `api.ts` 保留后端响应信封；`useRequest` 与 `usePage` 分别处理单对象和分页   | 防止 BUG-001 的重复解包问题再次出现   |
| 渐进式演进   | 当前先以“页面即功能切片”实现，未强加全局状态库或复杂实体层                  | 项目规模与抽象成本匹配，学习路径清晰  |

## 为什么没有完整使用 FSD

完整 FSD 还会细分 `entities`、`widgets`、`pages`、每个切片的公开 API 等层。对当前参考项目而言，商品和订单只有少量页面，过早引入这些层会产生“为了目录而目录”的成本。

因此这里采用 FSD 的核心原则，而非完整规范：

- 业务文件按领域聚集；
- 真正通用的能力才进入 `components`、`hooks`、`lib`；
- 共享层不能反向引用某个具体业务功能；
- 当某个领域出现多个页面、可复用实体组件或复杂状态时，再在 `features/<domain>/` 内增加 `ui/`、`api/`、`model/` 等子目录。

## 何时调整架构

- **加入 TanStack Query**：保留 `features` 边界，把 `usePage` 逐步替换为各功能域的 query/mutation；不要把 Query Key 散落在页面 JSX 中。
- **商品/订单跨多页复用**：增加 `entities/product`、`entities/order`，集中类型、展示组件和字段转换。
- **权限、通知、主题成为全局能力**：放到 `app/` 或共享 Provider，而不是塞进 `ConsoleLayout`。
- **单个功能超过约 3–5 个组件或出现专属请求/状态**：在该功能目录内部再分 `ui/`、`api/`、`model/`、`lib/`，不需要全项目同步大迁移。

## 评审检查清单

1. 新代码是否属于一个明确业务域？是则优先放入对应 `features/<domain>`。
2. 组件若不知道商品、订单等字段，是否应提升为 `components/ui`？
3. 是否有共享层导入了具体 Feature？若有，先抽出共享类型、回调或接口。
4. 状态是否只被一个页面使用？是则保持局部；多个页面需要协调时才上移。
5. 新接口响应是单对象还是分页？必须选择 `useRequest` 或 `usePage` 中正确的一个。
